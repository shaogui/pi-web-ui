# 消息同步（私聊 + 群）× 私聊提醒：一个引擎，两个面（`lib/dm-watch.mjs`，0.14.0）

需求原话：「私聊和群消息的拉取机制完善下，当前 webui 上只能看到私聊提醒的轮询，没看到消息同步相关的控制」。

这句话里其实藏了两件事：

1. **能力缺口**：后台轮询只拉单聊（`candidateChats()` 里 `chats.filter(c => c.p2p)`），群消息只能靠
   「打开会话」才进本地缓存 —— 于是群在列表上没有最后一条预览、没有未读、也搜不到；
2. **控制面缺口**：设置页只有一张「私聊提醒（轮询）」卡，用户在会话页看不到「同步到底开没开 /
   刚同步了几条」，也不知道群消息归谁管。

0.14.0 的结论是：**这两件事是同一个引擎的两个面，不该有两个开关、两份定时器**。

---

## 1. 为什么坚持「一个引擎」

| 若拆成两套（同步 / 提醒各一份）          | 后果                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------- |
| 两份候选会话清单                         | 单聊被拉两次（提醒一次、同步一次），lark-cli 子进程与配额直接翻倍                     |
| 两份水位                                 | 同一批消息在两套逻辑里算出不同的「新」，一边报过一边没报过 → 已读又变未读、提醒重复弹 |
| 两份本地缓存                             | 界面读哪一份都可能缺消息；`im_search` / 待办提取拿到的内容取决于「谁最后写的」        |
| 两个配置对象（间隔 / 范围 / 通知各一份） | 用户在 A 卡关了群、B 卡又打开 —— 这类"互相打架的设置"是最难排的 bug                   |

所以：**同一轮轮询、同一份水位、同一份缓存、同一份配置**，差别只在「要不要弹通知」。

```
                     ┌──────────────── lib/dm-watch.mjs（唯一轮询引擎）────────────────┐
 每 intervalSec ───▶ │ discover（im +chat-list，一次拿 p2p + group）                    │
                     │   ├─ 候选 = 手填 → 自动发现单聊(30) → 自动发现群(20)             │
                     │   ├─ 逐会话串行拉增量（--order desc --start <水位>）             │
                     │   │   缓存还没一屏时改拉最新一页（needsBackfill，见 §2.1）        │
                     │   ├─ 新消息 → 水位推进 + unread 累计 + history                   │
                     │   └─ onFetched(kind) ──▶ chatCache.put()（内容落本地缓存）       │
                     └───────────────┬───────────────────────────────┬─────────────────┘
                                     │ pickNotifyRecords()           │ onNew()
                              （私聊/手填才弹，群默认静默）      自动问答（白名单闸门）
```

## 2. 候选会话与预算（`buildPollCandidates`）

| 优先级 | 来源                             | 预算                                   | 备注                                                                  |
| ------ | -------------------------------- | -------------------------------------- | --------------------------------------------------------------------- |
| 1      | 手填 / 手动监听（`chatIds`）     | 计入对应种类预算，**永远排最前**       | 会话页「加入同步」按钮写的就是这份清单                                |
| 2      | 自动发现单聊（`chat_mode=p2p`）  | `MAX_CHATS_PER_POLL = 30`              | `autoDiscover` 打开才纳入（默认开）                                   |
| 3      | 自动发现群聊（其余 `chat_mode`） | `MAX_GROUPS_PER_POLL = 20`（**独立**） | `syncGroups` 默认**开**（群消息也要自动进缓存）；只有用户显式关掉才停 |

为什么群要独立预算：群的数量通常远多于单聊。共用一个 30 的上限时，26 个单聊就把名额吃光，
群永远轮不到（这正是 0.14.0 之前「只有私聊在轮询」的第二个成因）。

**为什么群同步默认开**（0.14.1）：群消息的自动获取和缓存是刚需（列表预览 / 未读 / 离线检索 / 待办提取
全都吃这份缓存），而副作用已被两条设计压住 —— 群有独立预算（不吃单聊名额）、
群消息默认**只同步不提醒**（`notifyGroups: false`）。关掉开关只影响后台自动拉，不影响打开会话时的按需拉。

> 配套不变式：缓存容量必须 ≥ 一轮候选数（`CHAT_CACHE_CHATS = 60 ≥ 30 + 20`）。
> 容量小于候选数时，每轮最后写入的群会被缓存裁剪掉 —— 表现为「同步在跑但群消息没进缓存」，
> 详见 [`chat-cache.md`](chat-cache.md#41-容量必须盖得住一轮轮询0141-修)。

成本口径（lark-cli 单次 spawn 实测 ≈25ms，见 [`dm-watch-lark-cli-eval.md`](dm-watch-lark-cli-eval.md)）：
30 单聊 + 20 群 = 50 次/轮；60s 间隔 ≈ 每天 1.8 分钟 CPU（单核 0.13%），30s 间隔 ≈ 0.25%。

真机实测（45 个候选 = 25 单聊 + 20 群，本机 lark-cli）：首轮建基线 **≈40s / 2135 条**，
之后每轮增量 **≈40s / 70 条**（每会话一次 CLI，串行）。间隔是**在上一轮结束后**才开始计的
（`tick()` 里 `schedule()` 在 finally），所以 60s 间隔的实际周期是「轮询时长 + 60s」，
不会出现两轮叠在一起。会话更多就调大间隔（30–900s 都支持）：
`im/v1/messages` 侧 50 次/分钟 ≈ 0.75 QPS，离飞书限流还很远，真正的成本是本机 CLI 子进程。

### 2.1 补屏：缓存还没一屏时不准只拉增量（0.14.1 修）

增量拉取（`--start <水位>`）只带得回「水位之后的消息」—— 它能维持水位，**但补不进缓存里没有的历史**。
而水位（0.10 起）比缓存（0.13 起）活得久：升级后第一轮就是增量，于是每轮只写进去 1 条，
缓存里每个会话永远只有 1 条（打开会话只看得到一条）。

所以引擎多了一个钩子：宿主传 `needsBackfill(chatId)`，返回 true 时**这一轮对该会话不带 `--start`**
（`startMs: 0`，`maxPages: 1`，拿最新一页 40 条），并在 `onFetched({ backfill: true })` 里告知宿主
「缓存从这一刻起有一屏了」。

代价：**0 次额外 CLI 调用**（这一轮本来就要拉这个会话），只有当轮多带回一屏历史；
通知口径不变 —— `pickNewMessages` 仍按水位过滤，补屏带回来的历史不会被当成新消息弹出来。
自述字段：`lastPoll.backfill` = 本轮补了几个会话的屏（界面能看出「为什么这轮条数多」）。

## 3. 通知分线（`pickNotifyRecords`）

「同步」不等于「打扰」。一条新消息进缓存是无声的，弹不弹看这张表：

| 会话来源        | 句柄                       | 默认                             |
| --------------- | -------------------------- | -------------------------------- |
| 手填 / 手动监听 | 一律弹（含群）             | 弹                               |
| 自动发现的单聊  | `notify`                   | 弹                               |
| 自动发现的群聊  | `notify` && `notifyGroups` | **不弹**（但**照常同步进缓存**） |

`notify = false` 时一条都不弹（同步照跑）。通知文案会带上被静默的条数
（`…（另有 N 条已同步未提醒）`）—— 宁可让人知道「还有消息没提醒你」，也别给一个看起来精确的假数字。

## 4. 控制面

### 4.1 路由

| 路由                | 说明                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /sync/state`   | **引擎状态 + 本地缓存自述**合成一份（界面只读这一份，不会「轮询在跑但缓存没东西」信息割裂）                                                                             |
| `POST /sync/config` | 改范围 / 间隔 / 通知 / 手填清单（与 `/dm/config` 同一个配置对象，只少一层 `config` 包裹）                                                                               |
| `POST /sync/run`    | 立刻同步一轮（`force`，与定时轮询同一条路径、同一个 `polling` 闸门）：先**有限等待**在飞的那轮（≤60s），等到了就直接用它的结果（不再白拉一遍），等不到回 `skipped=busy` |
| `POST /sync/clear`  | 只清缓存内容，**不动水位与配置**（所以下一轮只补最近的消息，不会把历史当新消息弹一遍；清完后每个会话都缺一屏 → 下一轮会走 §2.1 的补屏）                                 |

`/dm/*` 全部保留（`state` / `config` / `poll` / `discover` / `read`）：它是引擎原有入口，
自动问答、待办提取、未读徽标都还在用；`/sync/*` 是给人用的控制面。

为什么缓存统计不塞进 `/dm/state`：那个路由被会话页每 15s 轮一次，而 `chatCacheStats()` 要遍历整份
缓存并算字节数 —— 「看未读」这种高频请求别干重活。

### 4.2 界面

| 位置                            | 内容                                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 会话页顶部状态条（0.14.0 新增） | 开关状态 · 间隔 · 候选会话数（`N 私聊 / M 群`）· 上轮「X 会话 / Y 条 / 新增 Z」；配「立即同步」「同步设置」                                       |
| 设置页「② 消息同步与提醒」      | 启用 / 间隔 / 同步私聊 / 同步群聊 / 私聊弹通知 / 群消息也弹通知 / 手填会话 ID（折叠）/ 立即同步 + 状态行；改动后卡底出「撤销 / 保存并生效」动作条 |
| 设置页「④ 诊断与数据」          | 缓存体积与条数、上一轮拉取、候选会话、每会话同步状态（种类、最近同步、缓存条数、未读、错误）、最近提醒、危险操作（二次确认）                      |
| 会话列表每行                    | 「同步中」标签 + 未读徽标（徽标来自轮询累计，打开会话即清零 `/dm/read`）                                                                          |
| 会话详情头部                    | 「加入同步 / 移出同步」＝ 把会话写进手填清单（无论单聊群聊都会同步并提醒）                                                                        |

`client/sync-panel.mjs` 取代了 0.13.x 的 `client/dm-panel.mjs`（同名卡片换成一张，写一个配置对象）。
0.15.0 起它只渲染**表单体**（`{ call, onDirty, onState }` → `{ apply, save, revert, refresh, destroy }`），
卡头、状态胶囊、卡底动作条与审计清单都归 `client/settings-view.mjs`：状态只有一份 `/sync/state`（设置页拉、面板吃）。
会话页状态条只做「状态 + 一键触发」，**开关仍然只有一个地方**（设置页「② 消息同步与提醒」），避免两处配置打架。

## 5. `status()` 的形状（`/dm/state`、`/sync/state` 共用）

```js
{
  config: { enabled, intervalSec, identity, chatIds, autoDiscover, syncGroups, notify, notifyGroups },
  running, busy, lastError,
  candidates: { total, p2p, groups, explicit, budget: { chats: 30, groups: 20 } },
  lastPoll:   { at, chats, rows, fresh, truncated, errors },
  chats: [ { id, name, kind: "p2p"|"group"|"unknown", explicit, notify,
             watermarkMs, unread, syncedAt, lastError } ],
  unread: { "oc_…": 3 },
  discovered: { total, p2p, groups, at, error },
  history: [ …最近 50 条新消息（带 chatKind）… ]
}
```

`chats` 的口径是**真的在轮询的候选**（手填 → 私聊 → 群），不是「发现了但没拉」的一大堆：
这一列在界面上是「同步状态表」，混进不拉的会话只会让「多久没同步」变成假信息。

## 6. 排错

| 症状                    | 先看什么                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------- |
| 状态条「同步未启用」    | 设置页卡片没勾「启用后台同步」；或 `config.enabled=false`                                                     |
| 候选里有 0 个群         | 没勾「同步群聊」；或 `discovered.groups === 0`（lark-cli 没返回群 → 检查登录身份）                            |
| 会话行一直「未同步」    | `chats[].lastError`；CLI 未就绪时整轮 `no-channel`，状态条会写「lark-cli 未就绪」                             |
| 有新消息但不弹窗        | 群消息默认静默（勾「群消息也弹通知」）；或该会话不在手填清单且 `notify=false`                                 |
| 提醒重复 / 已读又变未读 | 水位 `{ ms, ids }` 的边界去重被绕过（见 README §9 的 0.10.22 补丁），别改成全局 `seen` 单挡                   |
| 缓存看着「很脏」        | 卡片上「清空消息缓存」（水位不动，下一轮补最近的增量）；体积口径见卡片底部的 `本地缓存：N 会话 / M 条 / X KB` |

## 7. 单测

`tests/unit/feishu-pro-message-sync.test.ts`：

- `normalizeDmConfig` 新字段：老数据回落、真值 coercion、幂等、间隔夹住、坏 id 丢弃；
- `buildPollCandidates`：手填优先、单聊/群各自预算、去重、非法 id、未知种类算单聊预算；
- `pickNotifyRecords`：`notify=false` 全静默、群默认静默、手填群照弹、脏记录不抛；
- 引擎端到端（假 storage + 假 CLI）：`syncGroups=false` 群不参与；打开后群进候选、内容经 `onFetched(kind)`
  落缓存、新消息**不弹**但 unread/水位照推；`notifyGroups=true` 才弹；`autoDiscover=false` 时手填会话照拉；
  `needsBackfill` 为真时 `startMs=0`（补屏）且 `onFetched.backfill=true`，水位照推、历史不误报。
