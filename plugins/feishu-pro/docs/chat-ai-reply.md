# 会话内 AI 回复（直接回复 / 预览回复）

在会话里**右键某一条消息**，弹出菜单选择「AI 直接回复这条」或「AI 预览回复这条」。
回复对象是**被右键的那条消息**（不是永远回复最新一条）：

| 模式         | 行为                                                                     | 适用场景                                     |
| ------------ | ------------------------------------------------------------------------ | -------------------------------------------- |
| **直接回复** | 生成后立刻以当前发送身份（我 / 机器人）发出去，内容不会先给你看          | 「回一句收到」「确认一下时间」这类低风险回复 |
| **预览回复** | 只生成，正文摊在输入框上方的预览面板里；**可编辑**，点「发送这条」才发出 | 对外承诺、报价、排期、需要斟酌措辞的回复     |

菜单里还有「复制文字」；右键时目标消息会描边，菜单关掉即撤掉。

## 为什么是右键，而不是输入框上方的按钮

回复的对象是**某一条**消息。「回谁」只有在消息本身上点才说得清 —— 群聊里同时有几条待回时，
顶栏按钮只能猜「最新那条」。右键菜单把目标、模式和身份一次讲清，也顺带给了一个复制入口。

与 `lib/auto-reply.mjs` 的关系：那边是**无人值守**引擎，判定逻辑（白名单 / 冷却 / 限频 / 陈旧）
是核心；这里是**人在场**的点按动作，判定就是那次右键 + 选择。两者只共用底层契约：
`host.chat` 派活、回执 `runId` 认领 `onRunEvent`、「宁可少发，不可重发」（发送失败不自动重试）。
代码上刻意分成两个模块，避免把「无人值守」的默认关 / 白名单空 = 谁都不回误加到手动操作上。

## 数据流

```
会话页（client/chats-view.mjs）
  ├─ contextmenu(row) → 菜单：AI 直接回复这条 / AI 预览回复这条 / 复制文字
  └─ POST /chat/ai-reply { chatId, mode: "preview" | "direct", as, instruction, messageId, uuid }
       ├─ chatMessagesPayload(chatId)      # 与界面同一个读出口（缓存优先，最多 60 条；提示词再截）
       ├─ chatAiReplier.generate(...)      # lib/chat-ai.mjs
       │    ├─ buildReplyPrompt(...)       # 锚点及之前 ≤12 条消息 + 回复要点 → 提示词
       │    ├─ host.chat({ text, accountId: "feishu-pro:chat-ai" })
       │    └─ onRunEvent(runId) → assistant 文本 → cleanAiReply
       ├─ mode=preview → 回 { text }，界面展示预览面板（可编辑）
       └─ mode=direct  → splitReplyText → sendChatText（同 `/chat/send` 的写通道）
```

预览面板的「发送这条」走 `POST /chat/send` —— 与手打消息同一条发送通道、同一套幂等键
（按生成轮次 / 失败那次派生，重试不重复发），不另造第二条发送路径。

## 锚点（`messageId`）

- 右键选中 `om_...` → 只取**它和它之前**的消息拼提示词，并给这一行打 `<-- reply to this`；
  更晚的消息不参与（否则模型会去回「后来那句」，而不是你点的那条）。
- 锚点不在本地缓存里（被轮询/预算刷掉）→ 直接报错「没找到要回复的那条消息」，
  不降级成无锚点回复（那等于悄悄回错对象）。
- 没有 `messageId` 的调用（兼容旧入口）仍按「最近消息」处理。
- 输入框上方的「回复要点」对两种模式都生效；切换会话会清空要点、锚点与预览草稿。

## 上下文隔离

`host.chat` 不带 `conversationId` 时用的是伪客户端的**当前活动会话**。所以账号按 chatId 派生
（`feishu-pro:chat-ai-<chatId>`，见 `chatAiAccountId`）：A 会话的草稿不会留在 B 会话的模型上下文里，
同一会话的「再生成」才会看到上一版。共用账号会让不相干的会话互相带偏，也把别的会话内容
带进不该看到它的那次生成。

## 提示词口径（`buildReplyPrompt`）

- **自包含**：把锚点及之前 ≤12 条消息（每条 ≤400 字，总预算 4000 字）贴进提示词，
  不让模型自己去翻会话 —— 少一次工具往返，也避免它顺手调用 `im_send` 真发出去。
- **明确只输出正文**：没有独立 system 通道，规则只能写在正文里：
  不要前言 / 引号 / 代码块 / 「回复：」前缀 / 签名。
- **先理解诉求再写**：要求模型先想清「对方真正要我做什么 / 我的下一步 / 哪些信息只有对方能给」，
  再落笔；不允许把「要我做的事」原样反问回去（群里那句「你想要什么账号和密码」就是反例）。
- **承接动作、不反抛决定**：开通 / 申请 / 审批 / 给权限这类「我职责内能办的事」，
  默认是「我来办 + 说明下一步 + 用标准默认值」，而不是让对方选账号类型、权限或密码。
- **最多问一个问题**：只有对方本人才知道的事实（邮箱 / 手机号 / 准确项目名）才值得问，
  且必须同时说明「我这边会做什么」。
- **不许编造**：不确定的细节就承诺跟进（「我确认后发你」），不能编事实、数字、链接、价格、期限；
  但「承诺去做一件常规的事」不算编造。
- **不许调工具**：发送由插件在用户决定后做，模型只负责写。
- 有「回复要点」时追加 `My intent for this reply: ...`（≤500 字）。
- 设置里填了「我的背景」（角色 / 能拍板的事 / 常用口径）时追加
  `About me (the account owner; trusted background): ...`（≤1000 字），
  与自动回复共用同一份配置。
- 一条可读消息都没有、也没填要点时，直接报错让用户先写一句，不空跑模型。

## 安全与失败语义

| 情况                  | 行为                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 同一会话已有生成在跑  | 服务端拒绝（`这个会话正在生成 AI 回复`）；右键菜单只留「复制文字」，连点不烧两份额度                                    |
| 生成超时（默认 180s） | 结束这一轮并回「AI 回复超时」，浏览器请求不会无限挂着                                                                   |
| 直发时发送失败        | **不自动重试**；未发出的正文回给界面并展开成预览；原样重发复用失败那段的幂等键（已发出则按 key 去重），改过字则用新 key |
| 内容 > 4000 字        | 直发按行切成 ≤3800 字的多条（幂等键带序号）；预览里发送前在界面拦下，让用户自己删                                       |
| 生成期间切走会话      | 结果丢弃（`selected?.id !== chatId`），预览草稿在切换会话时清空，避免把 A 的回复发到 B                                  |
| 插件重新加载 / 停用   | `chatAiReplier.stop()` 收掉还在等的调用，回「这一轮被取消」                                                             |

## 身份

- 默认跟随输入框上方的「我 / 机器人」开关；缺 `im:message.send_as_user` 时仍按既有提示
  让用户去重新授权或切机器人（与手发消息完全一致）。
- 直发前有一次 `confirm`（以谁的身份、发给哪个会话、内容不会先给你看）——
  这是唯一不可撤销的对外动作，一句确认比发错人便宜。
