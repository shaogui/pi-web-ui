# git-scm · 源代码管理

VSCode 式**源代码管理**面板：改动按**目录树**展示、逐文件/逐目录暂存与放弃、右侧**左右分栏** diff，
提交框里一个 ✦ 就能让 AI 按**仓库提交规范**生成结构化提交信息（标题行 + 正文 + 页脚），
分支 / 储藏 / amend / 撤销 / 标签 / revert / blame / 单文件历史这些常见操作也全在面板里。

> 与宿主内置 `git` 视图（`server/scm.ts`，只读）的分工：内置那个是「看」的，这个插件是「改」的
> —— 暂存 / 取消暂存 / 放弃 / 提交 / 拉取 / 推送 / 切分支 / init 全都在面板里完成。

## 界面（左栏 → 右栏）

| 区域      | 内容                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 头栏      | 刷新（视图不可见时不刷新）、更多操作（见下方「⋯ 菜单」）                                                                                                                                                                                          |
| 分支行    | 当前分支（点开 = **分支菜单**：新建 / 重命名 / 合并 / 删除 + 本地与远端分支）、`↑ahead ↓behind` /「无上游」、拉取 / 推送；点下去后**当前那个按钮转圈**、下方出现计时状态条（可取消）                                                              |
| 状态条    | 操作进行中：`⟳ 正在拉取（pull）… 4s` + 「取消」；结束：绿色回执（带 git 输出的首行）或红色错误原因，6 秒后自动消失                                                                                                                                |
| 提交框    | 多行消息（`Ctrl+Enter` 提交，随内容自动增高），右上角 ✦ = **AI 生成提交信息**（结果逐字流式写入）；下方「提交」与「全部暂存并提交」；amend 模式下按钮变「修正提交」且上方出现提示条                                                               |
| 更改区    | 两个分组：**暂存的更改**（porcelain 第一列）与**更改**（第二列 + 未跟踪），每组都是目录树：目录行有文件数、可折叠、可整目录暂存/取消暂存；文件行有状态字母（A/M/D/R/U）与 `+add/-del`，悬停出现 `+`（暂存）、`−`（取消暂存）、`↩`（放弃，带确认） |
| 储藏区    | 有 stash 时出现（可折叠）：每条显示说明与 `恢复并删除 / 恢复 / 删除` 三个小按钮；点一行 → 右栏看该储藏的完整补丁                                                                                                                                  |
| 提交历史  | 折叠在左栏底部（默认点开才拉取），点一条 → 右栏显示完整 patch；「只看这个文件」时只列该文件的提交                                                                                                                                                 |
| 右栏 diff | 默认**左右分栏**（旧文件 \| 新文件，行号各自成列、同行的删/增对齐，一侧缺行画斜纹），`@@` 蓝色、`+` 绿色、`-` 红色；头部按钮可切回单栏 unified（选择存 localStorage）；未跟踪文件由服务端合成「新文件」补丁，二进制/超大只给提示                  |

分隔条可拖拽（宽度存 localStorage，双击复位）。

## 常见 git 操作

### 分支菜单（点分支名）

| 项              | 行为                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------- |
| 新建分支…       | `git switch -c <name>`（失败回落 `checkout -b`），建完直接切过去                                     |
| 重命名当前分支… | `git branch -m <new>`                                                                                |
| 合并分支…       | 子菜单列其他本地分支，点一条 → `git merge --no-edit <name>`；冲突时黄条提示并在 ⋯ 里出现「取消合并」 |
| 删除分支…       | 子菜单列其他本地分支，点一条 → 确认后 `git branch -D <name>`（确认框已写明未合并会丢）               |
| 本地/远端分支   | 点一条即切换；`origin/x` 这类远端分支自动 `switch --track` 建同名本地跟踪分支                        |

分支名一律先过服务端 `isSafeRefName()`（拒 `-` 开头、空白、`..`、`@{`、`~^:?*[\`、`x.lock` 等）——
绝不把可疑字符串交给 git 去「解释」。

### ⋯ 菜单

| 项                                     | 行为                                                                                          |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| 发布分支 / 拉取变基 / 强制推送         | `push -u <remote> <branch>` / `pull --rebase` / `push --force-with-lease`（后者带二次确认）   |
| 获取（fetch）/ 取消合并                | `fetch --prune --all`；合并中才出现 `merge --abort`                                           |
| 储藏当前更改 / 含未跟踪                | `stash push [-u]`（不填说明就用 git 自己的 `WIP on <branch>: …`）                             |
| 修正上次提交（amend）                  | 拉出上一条提交的**完整消息**回填输入框并打上 amend 标记；这次提交 = `commit --amend`          |
| 撤销上次提交…                          | 子菜单：`reset --soft`（留暂存区）/ `--mixed`（留工作区）/ `--hard`（丢改动，二次确认）       |
| 创建标签…                              | 先问名字再问说明（留空 = 轻量标签），创建完再问要不要推到远端                                 |
| 添加远端…                              | 仓库还没配远端时才出现：填地址即 `git remote add origin <url>`（配好才能发布分支 / 推送标签） |
| 全部暂存 / 全部取消暂存 / 放弃所有更改 | 同前，破坏性操作都有 `confirm()`                                                              |

### 右栏头部

| 按钮              | 作用                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| 历史（钟）        | 左栏历史切换成**只看这个文件**（`log --follow -- <path>`），标题旁出现文件名 chip，点 × 恢复全部 |
| Blame（人像）     | 右栏切成**逐行追溯**：行号 / `哈希 作者 日期` / 正文；未提交行标「尚未提交」（再点一次收起）     |
| 还原（↩，历史里） | `git revert --no-edit <hash>`：生成一条反向提交，不改写历史；冲突时给「终止还原」入口            |

冲突中的仓库会在分支行显示 `⚔ N 冲突`（悬停列出文件），提醒先解决再继续。

## AI 生成提交信息（默认走仓库提交规范）

`POST /ai-message` → 服务端收集上下文（改动文件清单 + 暂存区/工作区补丁与每文件行数 + 未跟踪
文件名 + 最近 15 条提交主题）→ `host.llm.complete`（一次**孤立补全**：无工具、不建对话、不进历史、
只读 diff）→ 规范化 → 回填输入框。

### 结构化格式（`msgFormat = structured`，默认）

```
类型(影响范围): 摘要            ← 类型取自固定中文表；摘要祈使句、≤50 字、不加句号
                                  空行
- 修改背景：为什么改 / 解决什么问题 / 对应什么需求
- 改动详情：具体改了什么、核心逻辑变化
- 影响范围：涉及模块、副作用或风险
- 优化效果：有量化数据时补（可选）
                                  空行
关联 #123 / 关闭 #456 / 破坏性变更: … / 回滚 abc1234 …   ← 页脚，只写确有其事
```

固定类型表：**新增 / 修复 / 优化 / 重构 / 文档 / 格式 / 测试 / 构建 / 运维 / 清理 / 回滚**。

服务端 `normalizeCommitMessage()` 兜底执行规则（模型再乖也会跑偏）：

| 情况                                                                                       | 处理                                                                                                                                   |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 套代码围栏 / 写「提交信息：」标签 / 加引号 / 全角括号冒号                                  | 剥掉并归一成 `类型(范围): 摘要`                                                                                                        |
| 写成 conventional commits（`feat:` / `fix:` …）                                            | 映射回固定中文类型（feat→新增、fix→修复…）                                                                                             |
| 类型不在固定表                                                                             | 标题打 `???` + `problems` 提示                                                                                                         |
| **只有标题、没有正文**                                                                     | 带「必须补至少 2 点正文」的纠正指令**自动重试一次**；仍只有标题则保留标题并回 `problems`                                               |
| 正文不足 2 点 / 只有页脚 / 出现「修复bug」「优化一下」等模糊表述                           | 记进 `problems`（界面黄条）                                                                                                            |
| 页脚写成 `关联 #…` 等                                                                      | 单独拎出来，保证「正文 / 空行 / 页脚」三段结构                                                                                         |
| 吐工具调用 / 控制标记（`<\|DSML\|…>`、`<tool_calls>`、`<\|end_of_sentence\|>`）或整段 JSON | 先剥掉标记；剥完只剩标点或仍是 JSON 就算「不是提交信息」：带明确指令**重试一次**，仍不行回 `{ok:false}` 报错，**绝不把垃圾回填输入框** |

UI 侧两道闸：黄条 `AI 生成提醒` 列出 `problems`（手改消息即消失）；**提交时若消息缺正文**（只有
标题或只剩页脚），`confirm()` 用大白话问一次「仍要提交吗」——不硬拦，但绝不悄悄提交单句。

### 流式写入（`host.llm.complete` 没有 token 流）

宿主的一次性补全接口返回整段文本，所以面板做了两段体验上的「流」：

1. **等待期**：提交框上方状态条显示 `⟳ AI 生成中… 3s`（每秒刷新），不会看起来像卡死；
2. **到达后**：把整段按帧逐字注入提交框（约 0.6–1s，输入框随内容长高，光标跟在末尾）。
   写入期间提交按钮置灰（不允许提交半截消息）；再点一次 ✦、或开始手打，立刻补全/接管。

### 跟随仓库风格（`msgFormat = repo`）

单行 conventional commits 风格的仓库可以切到这一档：提示词改成「照抄仓库既有提交信息的格式与
语言」，输出压成一行（`sanitizeCommitMessage`），不做结构化改写。`language` 设置只在这一档生效。

其余约定：

- 提示词有 8000 字预算（宿主硬上限）：补丁按 3600 字截断、文件清单最多 60 行、总量再兜底截断。
- `llm.complete` 的 `maxChars = 1200`（结构化消息比单行长），模型可指定；留空 = 跟随默认。
- 生成失败把原因显示在提交框下方（红条），不动输入框里已有的手写内容。

## 设置

| 键               | 作用                                                                |
| ---------------- | ------------------------------------------------------------------- |
| `model`          | AI 生成用的模型；空 = 跟随默认                                      |
| `language`       | `auto` / `zh` / `en`（只对新仓库生效，已有提交时仍以仓库风格为准）  |
| `aiPromptMode`   | 自定义提示词的生效方式：`append`（拼在后面）/ `replace`（整份替换） |
| `aiPrompt`       | 自定义提示词                                                        |
| `refreshSeconds` | 自动刷新间隔（0 = 只手动刷新；超大仓库调大或关掉）                  |
| `gitBin`         | git 可执行文件路径（空 = PATH 里的 git；便携版填绝对路径）          |

## 工程约定（踩过的坑）

- 所有 git 命令走 `execFile/spawn("git", [argv...])`，**不过 shell**：路径含空格天然正确，也不会有
  引号/转义/注入面。`git clean`、`git rm` 这类破坏性命令一律带 `--` 与显式 pathspec。
- 网络操作（pull/push/fetch/publish）用 `spawn` + 自己结算，**不等 stdio 关闭**：实测 `git fetch`
  会再拉起 `git-remote-https`，孙进程握着管道时 execFile 的回调可能永远不触发（面板一直转圈）。
  取消走 `state.cancel()`：整组 kill（POSIX `-pid` / Windows `taskkill /T`）后立刻回「已取消」。
- 子进程环境固定 `GIT_TERMINAL_PROMPT=0` / `GIT_EDITOR=true` / `GIT_PAGER=cat`：凭据提示、
  编辑器、分页器都会把 HTTP 请求挂到超时。
- 读状态用 `git status --porcelain=v1 -z -b`：NUL 分隔，路径里的空格/引号/非 ASCII 都不用反转义；
  重命名记录后面那条「原路径」会被吃掉。
- 每个 git 调用都有超时与输出上限；普通命令 20s，pull/push/fetch 180s；单文件 diff 400KB 截断。
- 路由永远回 200 + `{ok}`：前端不需要 try/catch fetch，异常一律变 `{ok:false,error}`，绝不 500。
- 纯函数（porcelain 解析 / 提示词装配 / 消息清洗）内联在 `index.mjs` 里导出给单测 —— 宿主 reload
  只给 `index.mjs` 加 `?e=` 击穿缓存，兄弟模块改了不生效（必须重启服务）。
- 客户端 `entry.mjs` 顶层不碰 `document`，纯函数（建树 / 分组 / 补丁解析 / 宽度夹取）可直接在 node
  里 import 单测；样式内联在 bundle 里，reload 即生效。

## 与「编辑器 Pro」的联动（vscode-editor-pro）

两个插件互不 `import`（client bundle 只服务自己的 `client/` 子树），联动走**页内契约**，
装没装都不影响任何 git 能力：

| 方向             | 触发                                                   | 机制                                                                                                                                                                                                                 |
| ---------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A（本 → 编辑器） | 右栏头部 📄 按钮；**blame 里点任意一行**（定位到该行） | `window.__piVproEditor.open(req)`，返回 `true` = 受理；同时派发 `pi:vpro:open`（cancelable）并写待办槽 `window.__piVproPending` 兜 bundle 还没挂载的竞态，受理后 `__piWebUiHost.setView("plugin:vscode-editor-pro")` |
| C（编辑器 → 本） | 编辑器 Ctrl+S 保存 / 批量替换                          | 编辑器回叫 `window.__piGitScm.refresh()`（120ms 合并），本面板**立刻**重取 status + 当前 diff，不等 `refreshSeconds` 轮询                                                                                            |

请求体 `buildEditorOpenRequest()`：`{ source, path(仓库相对), absPath, line, repoRoot, workspace }`。
带绝对路径是刻意的 —— 仓库根未必等于编辑器的工作区根（工作区只是仓库子目录、或嵌套仓库时），
由编辑器用自己的根折算相对路径，两边都不靠猜。

未装编辑器：点按钮只出一条黄条提示（「插件市场搜 vscode-editor-pro」），**不报错、不改任何状态**。
文件在编辑器工作区外：同样只提示一句（`open()` 同步回 `false`，所以发起方不必先切视图）。

## 端点（`/plugins-api/git-scm/*`）

```
GET  /status         分支 / ahead-behind / 文件清单 / 每文件行数 / 本地分支 / 远端分支 / 标签 / 储藏 / 上次提交 / 冲突 / 合并中状态 / refreshSeconds
GET  /diff           ?path= 单文件 staged + worktree 补丁（未跟踪文件合成新文件补丁）
GET  /log            ?limit= 最近提交；?path= 只看该文件（--follow）
GET  /commit         ?hash= 单条提交完整 patch
GET  /commit-message ?hash=HEAD 提交消息原文（amend 回填）
GET  /blame          ?path= 单文件逐行追溯（--line-porcelain，最多 5000 行）
GET  /stash          ?index= 单条储藏的补丁
POST /stage          { paths? , all? }
POST /unstage        { paths? , all? }
POST /discard        { paths? , all? }   ← 未跟踪 clean；本次新增（A）从索引移除并删文件；其余按索引回写
POST /commit         { message, stageAll?, amend? }   ← 空行分段 → 多个 -m（主题 + 正文）
POST /sync           { action: "pull" | "pull-rebase" | "push" | "push-force" | "fetch" | "publish", opId? }
POST /sync/cancel    { opId }            ← 整组 kill 在飞的网络操作，回 { ok, code: "cancelled" }
POST /branch         { action: "switch" | "create" | "delete" | "rename", name, from?, force? }
POST /merge          { name, noFf? } | { abort: "merge" | "revert" | "cherry-pick" }
POST /reset          { mode: "soft" | "mixed" | "hard", count? }   ← 撤销最近 N 次提交
POST /revert         { hash }             ← 反向提交；冲突回 code:"conflict" + conflicts[]
POST /stash          { action: "save" | "pop" | "apply" | "drop" | "clear", index?, message?, includeUntracked?, opId? }
POST /tag            { action: "create" | "delete" | "push", name, message?, remote?, opId? }
POST /remote         { action: "add" | "remove", name, url? }   ← 新仓库补齐 origin
POST /init
POST /ai-message     { lang? }   ← 回 { ok, format, message, title, problems[], model }
```

合并 / 还原遇到冲突时统一回 `{ ok:false, code:"conflict", conflicts:[...], error }`（不 500），
前端据此在顶部黄条里说明「解决冲突后提交，或用「取消合并」放弃」。
